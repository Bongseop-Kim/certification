# 3과목. 어플리케이션 보안 — 4장

> 웹·DB·시큐어코딩은 강점 영역. **취약점 유형 명칭 + 대응기법 명칭**까지만 복원한다.

## 시트 3-1. FTP · 메일 보안

### FTP Active vs Passive

| 구분 | 제어 채널 | 데이터 채널 | 방화벽 |
|---|---|---|---|
| **Active** | 클라이언트 → 서버 **21** | 서버 **20** → 클라이언트 임의 포트 (서버가 접속) | 클라이언트 방화벽에서 차단되기 쉬움 |
| **Passive** | 클라이언트 → 서버 21 | 클라이언트 → 서버 임의 포트 (클라이언트가 접속) | 클라이언트 측 유리, 서버 포트 개방 필요 |

- Active: 클라이언트가 `PORT` 명령으로 자신의 포트를 알림
- Passive: 클라이언트가 `PASV` 명령 → 서버가 포트를 알림

### FTP 공격·대응

| 항목 | 내용 | 대응 |
|---|---|---|
| **Bounce Attack** | `PORT` 명령에 제3자 IP·포트를 지정해 FTP 서버가 대신 스캔·전송 | PORT 명령의 IP 검증, Passive 사용 |
| Anonymous FTP | 익명 접속 → 업로드 디렉터리 악용 | 익명 계정 제거, 쓰기 권한 차단 |
| TFTP (69/UDP) | **인증 없음**, 설정 파일 유출 | 불필요 시 서비스 중지 |
| 평문 전송 | 계정·데이터 스니핑 | **SFTP(22) / FTPS(TLS)** 사용 |
| 접근 제어 파일 | `/etc/ftpusers`(또는 ftpd.conf) 에 접속 차단 계정 등록, root 차단 | — |

### 메일 프로토콜

| 프로토콜 | 포트 | 역할 |
|---|---|---|
| SMTP | 25 (submission 587, SMTPS 465) | 발신 |
| POP3 | 110 (995) | 수신 — 서버에서 내려받고 삭제 |
| IMAP | 143 (993) | 수신 — 서버에 보관, 다중 기기 동기화 |
| MIME | — | 멀티미디어·첨부 인코딩 (Base64) |

### PGP vs S/MIME

| 항목 | PGP | S/MIME |
|---|---|---|
| 신뢰 모델 | **신뢰의 웹** (사용자 상호 서명) | **X.509 / CA 계층 구조** |
| 키 관리 | 사용자 자율 | CA 발급 인증서 |
| 표준화 | 사실상 표준 | IETF 표준, 기업 환경 |

**PGP 5대 기능**: 기밀성(대칭키 + 세션키 공개키 암호화) / 인증(전자서명) / 압축(ZIP) / 이메일 호환성(**Radix-64**) / 단편화

### 스팸·위조 메일 대응

| 기술 | 원리 |
|---|---|
| **SPF** | 도메인 DNS TXT에 **발신 허용 IP** 목록 등록 |
| **DKIM** | 발신 서버가 메일에 **전자서명**, 수신자가 공개키(DNS)로 검증 |
| **DMARC** | SPF·DKIM 실패 시 처리 **정책**(none/quarantine/reject) + 리포팅 |
| RBL / DNSBL | 스팸 발송 IP 블랙리스트 조회 |
| 릴레이 제한 | Open Relay 차단 (`/etc/mail/access`) |
| 베이지안 필터 | 통계 기반 스팸 분류 |

**함정 포인트**
- **Active는 서버가 클라이언트로 접속**한다(20번에서). 방향을 뒤집어 낸다.
- POP3는 내려받고 삭제, IMAP은 서버 보관. 차이를 묻는다.
- **SPF(IP) / DKIM(서명) / DMARC(정책)** 3종의 역할을 바꿔 낸다.
- PGP의 이메일 호환성 수단은 Radix-64(Base64)다.

📍 [3과목 어플리케이션보안] 1. 인터넷 응용 보안 > FTP 보안, 메일 보안(공격유형과 대책, 보안기술)

## 시트 3-2. DNS 보안

### 레코드 종류

| 레코드 | 의미 |
|---|---|
| **A** | 도메인 → IPv4 |
| **AAAA** | 도메인 → IPv6 |
| **CNAME** | 별칭(정규 이름 매핑) |
| **MX** | 메일 서버 (우선순위 값 포함) |
| **NS** | 네임서버 지정 |
| **PTR** | IP → 도메인 (역방향 조회) |
| **SOA** | 영역 권한 정보 (Serial, Refresh, Retry, Expire, TTL) |
| **TXT** | 임의 텍스트 → **SPF·DKIM·DMARC 등록 위치** |
| SRV | 서비스 위치(포트 포함) |

### 질의 방식
- **재귀적 질의(Recursive)**: 클라이언트 → 로컬 DNS. 최종 답을 대신 찾아 반환
- **반복적 질의(Iterative)**: 로컬 DNS → 루트 → TLD → 책임 서버 순차 조회

### 공격 유형

| 공격 | 원리 |
|---|---|
| **DNS 스푸핑** | 정상 응답보다 먼저 위조 응답을 보내 잘못된 IP 반환 |
| **DNS 캐시 포이즈닝** | 로컬 DNS **캐시**에 위조 레코드를 심어 지속적으로 오염 |
| **Zone Transfer 취약** | 인가되지 않은 대상에 존 정보 전체 유출 (TCP 53) |
| **DNS 증폭(DRDoS)** | 위조 출발지 + 개방 리졸버로 대량 응답 유발 |
| DNS 터널링 | DNS 질의에 데이터를 실어 정보 유출·C2 통신 |
| **Pharming** | 호스트 파일·DNS 조작으로 정상 URL 입력에도 위조 사이트 유도 |

### 대응 기술

| 대응 | 내용 |
|---|---|
| **DNSSEC** | 레코드에 전자서명. **RRSIG(서명) / DNSKEY(공개키) / DS(위임 서명자) / NSEC(부재 증명)** — 무결성·출처 인증 제공, **기밀성은 미제공** |
| Zone Transfer 제한 | `allow-transfer`로 보조 네임서버만 허용 |
| 재귀질의 제한 | 내부 사용자에게만 허용, 개방 리졸버 차단 |
| 버전 정보 은닉 | BIND 버전 배너 숨김 |
| 캐시 보호 | 소스 포트 무작위화(0x20 인코딩), TTL 관리 |

**함정 포인트**
- **DNSSEC은 암호화(기밀성)를 제공하지 않는다.** 무결성·인증만 제공한다. 최다 함정.
- 스푸핑(1회성 위조 응답) ↔ 캐시 포이즈닝(캐시 지속 오염) 구분.
- 존 전송은 **TCP** 53, 일반 질의는 UDP 53.
- SPF/DKIM/DMARC는 모두 **TXT** 레코드에 등록된다.

📍 [3과목 어플리케이션보안] 1. 인터넷 응용 보안 > DNS 보안(개념/서비스 운영/공격유형/보안기술)

## 시트 3-3. 웹 · DB 보안

### 쿠키 보안 속성

| 속성 | 효과 |
|---|---|
| **HttpOnly** | JavaScript의 `document.cookie` 접근 차단 → **XSS로 세션 탈취 완화** |
| **Secure** | HTTPS 연결에서만 전송 → 스니핑 방지 |
| **SameSite** (Strict/Lax/None) | 크로스 사이트 요청 시 쿠키 전송 제한 → **CSRF 완화** |
| Domain / Path | 전송 범위 한정 |
| Expires / Max-Age | 유효기간. 미지정 시 세션 쿠키 |

### 주요 웹 취약점 ↔ 대응기법 명칭

| 취약점 | 대응기법 |
|---|---|
| **SQL Injection** | 파라미터라이즈드 쿼리(Prepared Statement), 입력 검증, 최소 권한 DB 계정, 오류 메시지 은닉 |
| **XSS** (Stored / Reflected / DOM) | 출력 시 인코딩(이스케이프), 입력 검증, **HttpOnly**, CSP |
| **CSRF** | **CSRF 토큰**, Referer 검증, **SameSite**, 재인증 |
| **파일 업로드** | 확장자 화이트리스트, 실행 권한 제거, 웹루트 외부 저장, 파일명 변경 |
| **파일 다운로드 / 경로 조작** | `../` 필터링, 절대경로 사용 금지, 파일 식별자 간접 참조 |
| 디렉터리 리스팅 | `Options -Indexes` (자동 목록 비활성) |
| **세션 하이재킹 / 고정** | 로그인 시 **세션 ID 재발급**, 타임아웃, 예측 불가한 세션 ID |
| 명령 삽입 | 셸 호출 금지, 인자 검증 |
| 불충분한 인가 | 서버 측 권한 검증(직접 객체 참조 차단) |
| 리버스 텔넷 | 내부 → 외부 연결 차단(egress filtering) |

- **웹 로그 분석**: Common/Combined Log Format — 접속 IP, 시각, 요청 라인, **상태 코드**, 전송량, Referer, User-Agent

### HTTP 상태 코드

| 코드 | 의미 | 암기 포인트 |
|---|---|---|
| **200** | OK | 정상 |
| **301** | Moved Permanently | 영구 이동 |
| **302** | Found | 임시 이동 |
| **400** | Bad Request | 잘못된 요청 |
| **401** | Unauthorized | 인증 필요/실패 |
| **403** | Forbidden | 권한 없음 |
| **404** | Not Found | 자원 없음 |
| **500** | Internal Server Error | 서버 내부 오류 |
| **503** | Service Unavailable | 서비스 일시 불가 |

### DB 암호화 4방식

| 방식 | 위치 | 특징 |
|---|---|---|
| **API 방식** | 애플리케이션 | 응용 프로그램 수정 필요, DB 부하 적음 |
| **Plug-in 방식** | DB 서버(에이전트) | 응용 수정 불필요, DB 서버 부하 증가 |
| **TDE (커널)** | DBMS 자체 기능 | 성능 우수, DBMS 종속 |
| **하이브리드** | API + Plug-in | 컬럼별 선택 적용 |

### DB 접근통제·보안기술
접근통제(권한 최소화, 뷰 활용), 감사 로깅, DB 방화벽, 암호화, **뷰(View)** 를 통한 부분 노출 제어

### 개인정보 비식별화 기법

| 기법 | 예 |
|---|---|
| **가명처리** | 홍길동 → 임의ID_001 |
| **총계처리** | 개별값 → 합계·평균 |
| **데이터 삭제** | 식별자 컬럼 제거, 부분 삭제 |
| **범주화** | 나이 32 → 30대 |
| **데이터 마스킹** | 홍**동, 010-****-1234 |

**함정 포인트**
- **HttpOnly는 XSS 대응, SameSite는 CSRF 대응**. 짝을 바꿔 낸다.
- SQLi 대응의 1순위는 입력 검증이 아니라 **Prepared Statement**로 출제되는 경우가 많다.
- 세션 고정(Session Fixation) 대응은 로그인 성공 시 **세션 ID 재발급**이다.
- 비식별화 5기법의 명칭 자체를 고르게 한다. 특히 총계처리 ↔ 범주화 혼동.

## 시트 3-4. 전자상거래 보안

### SET 이중서명(Dual Signature)

**목적**: 판매자는 **지불정보(PI)** 를 볼 수 없고, 지불게이트웨이(PG)는 **주문정보(OI)** 를 볼 수 없게 하면서, 둘이 한 거래임을 증명

**생성 순서**
1. 주문정보(OI) 해시 → **H(OI)**
2. 지불정보(PI) 해시 → **H(PI)**
3. 두 해시를 연결(concatenate)
4. 연결값을 다시 해시 → **H( H(OI) || H(PI) )**
5. 이 값을 **고객의 개인키**로 서명 → 이중서명

**검증**: 판매자는 OI 원문 + H(PI)를, PG는 PI 원문 + H(OI)를 받아 각각 재계산해 서명 검증

**SET 구성 주체**: 카드 소지자 / 판매자(상인) / 발급기관(Issuer) / 매입기관(Acquirer) / **지불 게이트웨이(PG)** / 인증기관(CA)

### SSL vs SET

| 항목 | SSL/TLS | SET |
|---|---|---|
| 계층 | 전송 | 응용 |
| 적용 범위 | 통신 구간 암호화 | 지불 프로세스 전체 |
| 인증서 | 서버(선택적 클라이언트) | **모든 참여자** 필요 |
| 부인 방지 | 제한적 | 제공 |
| 판매자의 카드정보 열람 | 가능 | **불가(이중서명)** |
| 구현 복잡도·속도 | 단순·빠름 | **복잡·느림** → 사실상 미보급 |

### 전자화폐 요구조건

| 요건 | 내용 |
|---|---|
| **불추적성(익명성)** | 사용 내역으로 사용자를 추적할 수 없음 (→ **은닉서명** 활용) |
| **양도성** | 제3자에게 이전 가능 |
| **분할성** | 소액 분할 사용 가능 |
| **독립성(완전 정보화)** | 물리 매체 없이 디지털 정보만으로 가치 유지 |
| **이중사용 방지** | 동일 화폐 재사용 불가 |
| 위조 불가 | 복제·변조 방지 |

### 지불수단별 보안요소

| 수단 | 핵심 보안요소 |
|---|---|
| 신용카드 | 카드정보 기밀성, 부인방지, PG 경유, PCI-DSS(🟡 경계) |
| 전자수표 | 전자서명, 부인방지, 이중사용 방지 |
| 전자화폐 | 익명성, 이중사용 방지 |
| 계좌이체 | 사용자 인증(2요소), 거래 무결성 |

### 인증기술

| 기술 | 원리 |
|---|---|
| **OTP — 시간 동기** | 시각을 입력값으로 사용 (서버·토큰 시간 동기 필요) |
| **OTP — 이벤트 동기** | 카운터 증가값 사용 |
| **OTP — 챌린지-리스폰스** | 서버가 준 난수를 입력해 생성 |
| S/KEY | 해시 체인을 역순으로 사용하는 일회용 패스워드 |
| 전자서명·공인(공동)인증서 | X.509 기반 신원 확인, 부인방지 |
| 무선 플랫폼 | WPKI, WTLS (WAP 계열) — 경량 인증서·짧은 키 |

**함정 포인트**
- 이중서명의 해시 순서: **각각 해시 → 연결 → 다시 해시 → 서명**. "연결 후 한 번만 해시"로 바꾼 선지가 오답.
- 이중서명에서 **판매자가 못 보는 것은 지불정보(PI)** 다. 방향을 뒤집어 낸다.
- 익명성 확보 수단으로 **은닉서명**이 정답이 되는 문제가 자주 나온다.
- SET은 모든 참여자에게 인증서가 필요해 보급이 실패했다는 점이 단점 문항으로 출제된다.
