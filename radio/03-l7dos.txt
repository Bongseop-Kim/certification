정보보안기사 실기 라디오. 3편. 트래픽은 적은데 서버가 죽는 사건.

오늘 나오는 용어는 일곱 개입니다. 에이치티티피 겟 플러딩, 씨씨 어택, 슬로로리스, 슬로 에이치티티피 포스트, 슬로 에이치티티피 리드, 리밋 리퀘스트 바디, 타임아웃. 지난 편이 회선을 가득 채우는 공격이었다면, 오늘은 적은 트래픽으로 웹 서버만 골라 쓰러뜨리는 공격입니다.


첫 번째 장면. 정상처럼 보이는 손님들.

지난 디도스 사건 일주일 뒤, 쇼핑몰이 또 느려집니다. 그런데 이번에는 회선 사용량이 평소와 비슷합니다. 개발자가 박 선임을 찾아갑니다.

개발자가 말합니다. 회선은 멀쩡한데 웹 서버만 응답이 없어요. 신 리시브드 상태도 많지 않고요.

박 선임이 답합니다. 그럼 네트워크 계층이 아니라 응용 계층 공격을 의심해야 해요. 웹 서버 액세스 로그를 봐요.

로그에는 메인 페이지를 요청하는 겟 요청이 초당 수천 건 찍혀 있었습니다. 요청 형식은 완전히 정상이고, 아이피는 수백 개로 흩어져 있었습니다.

박 선임이 설명합니다. 에이치티티피 겟 플러딩이에요. 봇넷에 감염된 컴퓨터들이 정상적인 겟 요청을 대량으로 보내서 웹 서버 자원을 소진시키는 공격이에요. 세 번 악수를 정상적으로 마친 진짜 연결이라, 신 쿠키 같은 대응으로는 걸러지지 않아요.

여기서 잠깐 떠올려 보세요. 요청 하나하나가 정상인데 어떻게 공격을 걸러 낼까요?

답입니다. 양으로 거릅니다. 아이피 하나가 일정 시간에 보내는 요청 수에 임계값을 두고, 넘으면 차단합니다. 사람이라면 할 수 없는 속도이기 때문입니다.

정리합니다. 에이치티티피 겟 플러딩. 정상 겟 요청을 대량으로 보내 웹 서버 자원을 고갈시키는 공격. 대응은 아이피별 요청 수 임계값 차단.


두 번째 장면. 캐시를 건너뛰는 요청.

임계값을 걸자 요청 수는 줄었는데, 이번엔 원본 웹 서버만 유독 힘들어합니다. 쇼핑몰 앞에는 캐시 서버가 있어서, 자주 보는 페이지는 캐시 서버가 대신 응답합니다. 그런데 요청이 전부 캐시를 지나쳐 원본 서버까지 오고 있었습니다.

박 선임이 요청 헤더를 봅니다. 모든 요청에 캐시 컨트롤 헤더가 붙어 있었고, 값은 노 캐시와 노 스토어였습니다.

박 선임이 말합니다. 씨씨 어택이에요. 씨씨는 캐시 컨트롤의 약자예요. 캐시 컨트롤 헤더에 노 캐시를 넣으면 캐시 서버는 저장된 사본을 주지 않고 원본 서버에 새로 물어봐요. 공격자는 이걸 이용해서 캐시 서버를 무력화하고 원본 서버에 부하를 몰아요.

여기서 잠깐 떠올려 보세요. 씨씨 어택은 어떻게 막을까요?

답입니다. 캐시 컨트롤 헤더에 노 캐시가 붙은 요청이 짧은 시간에 몰리면 그 아이피를 차단합니다. 또 캐시 서버가 클라이언트의 캐시 컨트롤 값을 그대로 따르지 않도록 설정합니다.

정리합니다. 씨씨 어택. 캐시 컨트롤 헤더를 노 캐시로 조작해 캐시 서버를 우회하고 원본 웹 서버에 부하를 주는 공격. 겟 플러딩의 변형입니다.


세 번째 장면. 끝나지 않는 헤더.

며칠 뒤, 이번엔 요청 수가 분당 몇십 건밖에 안 되는데 웹 서버가 새 손님을 받지 못합니다. 웹 서버의 동시 접속 슬롯이 전부 차 있었습니다.

박 선임이 패킷을 봅니다. 한 연결에서 헤더가 한 줄씩, 수십 초 간격으로 아주 천천히 들어오고 있었습니다. 그리고 요청이 끝나지 않았습니다.

박 선임이 설명합니다. 에이치티티피 요청은 헤더가 끝나면 빈 줄이 와요. 캐리지 리턴 라인 피드가 두 번 연속으로 오는 거죠. 웹 서버는 이 빈 줄을 받아야 헤더가 끝났다고 판단해요. 공격자는 이 빈 줄을 절대 보내지 않고, 의미 없는 헤더를 조금씩 계속 보내요. 그러면 웹 서버는 연결을 끊지 못하고 계속 기다리죠. 이런 연결 몇백 개면 동시 접속 슬롯이 다 막혀요. 이게 슬로로리스, 다른 이름으로 슬로 에이치티티피 헤더 도스예요.

여기서 잠깐 떠올려 보세요. 헤더의 끝을 알리는 문자 두 개는 무엇일까요?

답입니다. 시알과 엘에프, 캐리지 리턴과 라인 피드입니다. 백슬래시 알, 백슬래시 엔이라고도 씁니다. 이게 두 번 이어지면 헤더가 끝나고 바디가 시작됩니다.

정리합니다. 슬로로리스. 헤더 끝을 알리는 빈 줄을 보내지 않고 불완전한 헤더를 천천히 보내 웹 서버 연결을 오래 점유하는 공격.


네 번째 장면. 한 글자씩 보내는 글쓰기.

슬로로리스를 막자 이번엔 포스트 요청이 문제가 됩니다. 헤더는 정상으로 끝났는데, 콘텐츠 렝스, 그러니까 바디 길이를 아주 크게 적어 놓고 바디를 몇 초에 한 바이트씩 보내고 있었습니다.

박 선임이 말합니다. 슬로 에이치티티피 포스트 공격이에요. 루디라고도 불러요. 서버는 콘텐츠 렝스만큼 다 받을 때까지 연결을 유지하니까, 바디를 아주 천천히 보내면 연결이 오래 붙잡혀요.

그다음 공격은 방향이 반대였습니다. 요청은 정상인데, 응답을 받는 클라이언트 쪽에서 티씨피 윈도우 크기를 영으로 알리고 있었습니다.

박 선임이 말합니다. 슬로 에이치티티피 리드 공격이에요. 윈도우 크기가 영이면 받을 공간이 없다는 뜻이라 서버는 응답을 보내지 못하고 기다려요. 그동안 연결이 계속 묶여 있죠.

여기서 잠깐 떠올려 보세요. 슬로 계열 공격 세 가지는 각각 어디를 늦출까요?

답입니다. 슬로로리스는 헤더를, 슬로 포스트는 바디를, 슬로 리드는 응답 수신을 늦춥니다. 공통점은 트래픽은 적지만 연결을 오래 붙잡는다는 것입니다.


다섯 번째 장면. 기다림에 한계를 두기.

박 선임이 아파치 설정으로 대응합니다.

첫째, 타임아웃 값을 줄입니다. 요청을 다 받을 때까지 기다리는 최대 시간입니다. 기본값이 길게 잡혀 있으면 느린 연결이 오래 버팁니다. 리퀘스트 리드 타임아웃 모듈을 쓰면 헤더와 바디를 받는 시간을 따로 제한할 수 있습니다.

둘째, 리밋 리퀘스트 바디로 요청 바디의 최대 크기를 제한합니다. 콘텐츠 렝스를 터무니없이 크게 잡는 슬로 포스트 공격을 막고, 큰 파일 업로드로 서버를 괴롭히는 것도 막습니다.

셋째, 아이피 하나가 동시에 맺을 수 있는 연결 수를 제한합니다. 슬로 공격은 한 곳에서 연결을 많이 붙잡는 방식이라 효과가 큽니다.

여기서 잠깐 떠올려 보세요. 아파치에서 업로드되는 요청 바디의 최대 크기를 정하는 지시어는 무엇일까요?

답입니다. 리밋 리퀘스트 바디입니다. 기존 실기 문항에도 업로드 용량 제한 설정으로 나왔습니다.

개발자가 말합니다. 지난번 디도스는 회선을 막고, 이번엔 문 앞에서 시간을 끄는 거네요.

박 선임이 답합니다. 맞아요. 그래서 대응도 달라요. 회선 공격은 회선 업체와 블랙홀 라우팅, 응용 계층 공격은 웹 서버 설정과 임계값이에요.


여섯 번째 장면. 로그로 구분하기.

개발자가 묻습니다. 다음에 또 느려지면, 어떤 공격인지 어떻게 빨리 알아요?

박 선임이 답합니다. 두 가지를 같이 봐요. 액세스 로그의 요청 수, 그리고 넷스탯의 연결 상태예요.

박 선임이 구분법을 정리합니다. 겟 플러딩과 씨씨 어택은 요청 수가 폭증합니다. 액세스 로그가 빠르게 쌓이고, 같은 주소를 반복해서 요청합니다. 씨씨 어택이라면 요청 헤더에 캐시 컨트롤 노 캐시가 붙어 있습니다.

반대로 슬로 계열은 요청 수는 적은데 이스태블리시드 상태 연결이 몇몇 아이피에 몰려 오래 유지됩니다. 요청이 끝나지 않으니 액세스 로그에는 오히려 잘 안 남고, 타임아웃으로 끊긴 요청은 사백팔, 리퀘스트 타임아웃 응답 코드로 남기도 합니다.

여기서 잠깐 떠올려 보세요. 요청 수는 적은데 연결이 오래 붙어 있다면 어느 계열 공격일까요?

답입니다. 슬로 계열입니다. 슬로로리스, 슬로 포스트, 슬로 리드 중 무엇인지는 헤더가 안 끝나는지, 바디가 느린지, 윈도우 크기가 영인지로 가립니다.


오늘의 정리.

에이치티티피 겟 플러딩. 정상 겟 요청 대량 전송. 대응은 아이피별 요청 수 임계값.
