정보보안기사 실기 궁금증 5편. 게시판 댓글 하나로 남의 계정을 훔칠 수 있을까?

인터넷 게시판에 댓글을 달면, 서버는 그 글을 저장했다가 다른 사람이 게시글을 열 때 화면에 그대로 보여 줍니다. 그런데 브라우저 입장에서 화면에 보이는 글자와 실행할 코드는 같은 에이치티엠엘 문서 안에 섞여 있습니다. 이렇게 검증되지 않은 외부 입력이 웹 페이지에 그대로 출력되어, 공격자의 스크립트가 다른 사용자의 브라우저에서 실행되는 취약점을 크로스 사이트 스크립팅이라고 합니다. 약자가 씨에스에스가 되면 스타일 시트와 겹치므로 엑스에스에스라고 부릅니다.

그런데 정말 댓글 하나 읽었을 뿐인데 내 계정이 남의 손에 넘어갈 수 있을까요?

이 궁금증을 풀려면 먼저 공격 코드가 어디서 실행되는지부터 알아야 하는데, 지난 편의 에스큐엘 인젝션은 서버의 데이터베이스에서 공격 코드가 실행됐습니다. 반면 엑스에스에스는 사용자의 브라우저에서 실행됩니다. 서버는 받은 내용을 그대로 내보냈을 뿐인데, 그 내용을 받은 브라우저가 그것을 코드로 해석해 실행하는 겁니다.

스크립트가 실행되면 그 사이트의 권한으로 무엇이든 할 수 있습니다. 가장 대표적인 피해는 쿠키 탈취입니다. 스크립트가 도큐먼트 점 쿠키 값을 읽어 공격자 서버 주소에 붙여 보내면, 쿠키에 담긴 세션 아이디가 공격자에게 넘어갑니다. 공격자는 그 세션 아이디로 피해자인 척 로그인한 상태가 됩니다. 즉 비밀번호를 몰라도 계정을 빼앗을 수 있는 겁니다. 이 밖에도 가짜 로그인 창 띄우기, 악성 사이트로 이동시키기, 피해자 권한으로 요청 보내기가 가능합니다.

실기에서는 엑스에스에스의 정의, 세 유형의 구분, 대응을 묻습니다. 유형 두세 가지를 골라 각각의 동작을 서술하라는 문제도 나옵니다.


그렇다면 엑스에스에스의 세 유형은 무엇이 다를까요?

처음 장면처럼 게시판, 댓글, 상품 리뷰처럼 내용이 저장되는 곳에 스크립트를 넣어 두면, 그 글을 조회하는 모든 사용자의 브라우저에서 스크립트가 실행됩니다. 이를 저장형, 스토어드 엑스에스에스라고 합니다. 스크립트가 서버의 데이터베이스에 저장되기 때문에 한 번 심어 두면 피해가 계속됩니다. 공격자가 피해자에게 링크를 보낼 필요도 없고, 인기 있는 게시글일수록 피해자가 많아집니다.

그런데 화면에는 평범한 한 줄만 보이는 경우가 많습니다. 스크립트는 저장된 원문에 숨어 있기 때문입니다. 그래서 조사할 때는 화면이 아니라 데이터베이스에 저장된 원문을 확인해야 하고, 대응도 입력할 때의 검증과 출력할 때의 인코딩을 모두 적용해야 이미 저장된 글까지 안전해집니다.

그럼 저장되지 않는 엑스에스에스도 있을까요? 있습니다. 스크립트가 요청 파라미터에 담겨 있다가, 서버 응답에 그대로 반사되어 실행되는 공격을 반사형, 리플렉티드 엑스에스에스라고 합니다. 검색 페이지가 입력한 검색어를 결과 화면에 그대로 보여 주는 경우가 전형적입니다. 공격자는 검색어 자리에 스크립트를 넣은 링크를 만들어 문자나 메일로 보내고, 피해자가 그 링크를 누르는 순간 스크립트가 실행됩니다. 저장되지 않으므로 링크를 누른 사람에게만 한 번 실행됩니다.

마지막은 서버를 아예 거치지 않는 유형입니다. 페이지의 자바스크립트가 주소창 값, 예를 들어 샵 기호 뒤의 값을 읽어 페이지 구조인 돔에 직접 그리는 과정에서 스크립트가 실행됩니다. 이를 돔 기반 엑스에스에스라고 합니다. 서버 응답에는 공격 코드가 없으므로 서버 로그에 흔적이 거의 남지 않습니다.

즉 세 유형은 스크립트가 어디에 있느냐로 갈리는 겁니다. 저장형은 서버 데이터베이스에, 반사형은 요청 파라미터에 담겨 응답으로 돌아오고, 돔 기반은 브라우저의 자바스크립트 처리 과정에서 실행됩니다. 기존 실기 문항에도 리플렉티드, 스토어드, 돔 기반을 빈칸으로 채우는 문제가 있습니다.


그렇다면 스크립트 태그라는 글자만 막으면 엑스에스에스를 막을 수 있지 않을까요?

그렇지 않습니다. 스크립트 태그 문자열만 필터링하면 쉽게 우회됩니다. 이미지 태그의 온에러 속성이나 대소문자를 섞은 태그처럼 스크립트를 실행하는 방법이 많기 때문입니다.

첫째 대응은 출력할 때의 인코딩입니다. 에이치티엠엘에서 특별한 의미를 갖는 문자를 에이치티엠엘 엔티티로 바꿉니다. 작다 기호는 앰퍼샌드 엘티 세미콜론, 크다 기호는 앰퍼샌드 지티 세미콜론으로, 앰퍼샌드와 큰따옴표, 작은따옴표도 각각 엔티티로 바꿉니다. 그러면 브라우저는 이를 태그가 아니라 화면에 보이는 글자로만 그립니다.

둘째, 입력 검증은 반드시 서버에서 합니다. 게시판에서 일부 에이치티엠엘 태그를 허용해야 한다면 허용할 태그만 정한 화이트리스트 방식을 씁니다.

셋째, 쿠키에 에이치티티피 온리 속성을 붙입니다. 이 속성이 붙은 쿠키는 자바스크립트로 읽을 수 없으므로, 스크립트가 실행되더라도 도큐먼트 점 쿠키로 세션 아이디를 훔쳐 가지 못합니다.

넷째, 콘텐츠 시큐리티 폴리시 헤더로 허용한 출처의 스크립트만 실행되게 합니다.

그럼 에이치티티피 온리만 붙이면 충분할까요? 에이치티티피 온리는 쿠키 탈취를 막을 뿐, 스크립트 실행 자체를 막지는 못합니다. 그래서 출력 인코딩과 함께 씁니다.


그런데 쿠키를 훔치지 않고도 남의 계정으로 일을 저지를 수 있다면 어떨까요?

사용자가 쇼핑몰에 로그인한 채로 공격자가 만든 외부 페이지를 엽니다. 그 페이지에는 쇼핑몰의 배송지 변경 주소로 요청을 보내는 숨은 폼이나 이미지 태그가 있습니다. 브라우저는 쇼핑몰로 가는 요청에 쇼핑몰 쿠키를 자동으로 붙여 보냅니다. 서버는 정상 세션 쿠키가 붙은 요청이므로 사용자가 직접 보낸 요청으로 믿고 처리합니다. 이처럼 로그인한 사용자가 자신도 모르게, 공격자가 의도한 요청을 서버에 보내게 만드는 공격을 사이트 간 요청 위조, 씨에스알에프라고 합니다. 공격자는 사용자의 비밀번호나 쿠키를 훔치지 않았습니다. 인증된 상태를 이용했을 뿐입니다.

그렇다면 이 공격은 언제나 성공할까요? 두 조건이 필요합니다. 피해자가 대상 사이트에 로그인되어 있어야 하고, 공격자가 요청의 파라미터를 모두 예측할 수 있어야 합니다.

여기서 엑스에스에스와 헷갈리기 쉽습니다. 엑스에스에스는 공격자의 스크립트가 사용자 브라우저에서 실행되는 공격으로, 사용자가 사이트를 믿는 점을 이용합니다. 씨에스알에프는 사용자가 원치 않는 요청을 서버로 보내게 하는 공격으로, 서버가 인증된 사용자를 믿는 점을 이용합니다. 즉 누가 누구를 믿는지가 반대인 겁니다.


그럼 서버는 이 요청이 사용자가 정말 보낸 것인지 어떻게 알 수 있을까요?

대응의 핵심은 요청이 정상 경로로 왔는지 서버가 확인하는 겁니다. 첫째, 씨에스알에프 토큰입니다. 폼을 보여 줄 때마다 예측할 수 없는 난수 토큰을 새로 만들어 폼의 숨은 필드와 사용자 세션에 함께 저장합니다. 요청이 오면 두 값을 비교해 다르면 거부합니다. 외부 페이지는 이 토큰 값을 알 수 없으므로 위조 요청이 실패합니다. 공격 조건 가운데 파라미터 예측을 끊는 겁니다.

둘째, 배송지 변경이나 결제, 비밀번호 변경 같은 중요한 기능은 비밀번호를 다시 묻는 재인증을 거칩니다. 셋째, 캡차로 사람이 직접 요청했는지 확인합니다. 넷째, 상태를 바꾸는 요청은 겟이 아니라 포스트로 받습니다. 겟 요청은 이미지 태그 하나로도 보낼 수 있어 위조가 더 쉽습니다. 다섯째, 쿠키에 세임사이트 속성을 걸어 다른 사이트에서 출발한 요청에는 쿠키가 붙지 않게 합니다. 리퍼러 헤더로 요청이 어디서 왔는지 확인하는 방법은 보조 수단입니다.

기존 실기 문항에는 씨에스알에프 대응으로 캡차, 재인증, 씨에스알에프 토큰을 빈칸으로 채우는 문제가 있었습니다. 실제로 2026년 1회 실기에는 씨에스알에프 대응 코드를 주고 보완 방법을 서술하라는 문제가 나왔고, 모범 답안에 토큰 비교, 재인증, 포스트 방식 사용이 들어갔습니다.


그런데 지금까지 쿠키와 세션이라는 말이 계속 나왔습니다. 둘은 정확히 무엇이 다를까요?

이 차이는 그 자체로 시험에 나옵니다. 2026년 1회 실기에 세션과 쿠키를 각각 서술하라는 문항이 나왔습니다. 쿠키는 상태 정보를 클라이언트, 즉 브라우저에 저장하고 요청과 응답 헤더에 실어 주고받는 방식입니다. 사용자가 직접 값을 볼 수 있고 고칠 수도 있으며, 암호화되지 않은 통신에서는 스니핑으로 노출될 수 있습니다.

세션은 상태 정보를 서버에 저장하는 방식입니다. 클라이언트에는 세션을 찾기 위한 세션 아이디만 쿠키로 줍니다. 중요한 정보가 서버에 있으므로 쿠키 방식보다 안전하게 상태를 유지할 수 있습니다. 다만 세션 아이디가 유출되면 그 세션을 빼앗길 수 있습니다.

그래서 세션 관리 보안이 함께 따라옵니다. 로그인에 성공하면 세션 아이디를 새로 발급해 세션 고정 공격을 막고, 일정 시간 동안 활동이 없으면 세션을 만료시키며, 로그아웃할 때 서버의 세션을 파기합니다. 쿠키에는 에이치티티피 온리와 함께, 에이치티티피에스로만 전송되게 하는 시큐어 속성과 세임사이트 속성을 붙입니다.


마지막 궁금증입니다. 입력창의 자바스크립트로 꺾쇠 기호를 막아 두었는데도 왜 엑스에스에스가 뚫릴까요?

브라우저에서 하는 검사는 웹 프록시로 바로 우회되기 때문입니다. 웹 프록시는 브라우저와 웹 서버 사이에서 요청과 응답을 가로채 확인하고 고칠 수 있는 도구입니다. 버프 스위트, 파로스, 피들러가 대표적입니다. 공격자는 브라우저 검사를 통과한 요청을 프록시에서 가로채 스크립트를 끼워 넣습니다. 즉 입력 검증은 반드시 서버에서 해야 하는 겁니다.

점검자 입장에서 피들러로 에이치티티피에스 사이트를 보려면 한 가지 설정이 필요합니다. 기본 상태에서는 암호화된 통신 내용을 볼 수 없습니다. 피들러 옵션에서 디크립트 에이치티티피에스 트래픽을 켜고, 피들러 루트 인증서를 클라이언트에 설치해야 프록시가 중간에서 복호화해 보여 줍니다. 실제로 2026년 1회 실기 실무형에는 피들러로 점검하는데 웹 트래픽 분석이 안 되는 이유와 해결 방법, 그리고 점검 중인 취약점과 대응을 묻는 문제가 나왔고, 그 취약점이 엑스에스에스였습니다.


정리해 보면, 댓글 하나로 계정을 빼앗기는 이유는 공격자의 스크립트가 내 브라우저에서 실행되어 쿠키를 훔쳐 가기 때문입니다. 저장형은 데이터베이스에 저장되어 조회하는 사람마다 실행되고, 반사형은 링크 파라미터가 응답으로 반사되며, 돔 기반은 브라우저 자바스크립트 처리 중에 실행됩니다. 대응은 에이치티엠엘 엔티티 치환, 서버 측 검증, 에이치티티피 온리, 콘텐츠 시큐리티 폴리시입니다. 씨에스알에프는 로그인한 사용자가 모르게 요청을 보내게 하는 공격으로, 서버가 사용자를 믿는 점을 이용하고, 대응은 씨에스알에프 토큰, 재인증, 캡차, 포스트 사용, 세임사이트입니다. 쿠키는 클라이언트에, 세션은 서버에 저장하며, 로그인할 때 세션 아이디를 새로 발급합니다. 피들러로 에이치티티피에스를 보려면 복호화를 켜고 루트 인증서를 설치합니다.
