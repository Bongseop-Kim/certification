정보보안기사 실기 궁금증 6편. 이미지 주소 하나로 내부 서버를 불러낼 수 있을까?

메신저나 게시판에 인터넷 주소를 붙여 넣으면, 잠시 뒤 그 페이지의 제목과 대표 이미지가 미리보기로 뜹니다. 우리 브라우저가 그 주소에 다녀온 것이 아니라, 서버가 대신 그 주소에 요청을 보내 내용을 받아 온 겁니다. 이렇게 서버가 사용자가 준 주소로 대신 요청을 보내는 기능에서, 그 주소를 검증하지 않아 공격자가 서버를 통해 내부망 자원에 접근하게 되는 취약점을 서버 측 요청 위조, 에스에스알에프라고 합니다.

그런데 정말 주소 하나만 바꿔 넣어서 바깥에서는 들어갈 수 없는 내부 서버를 열어 볼 수 있을까요?

이 궁금증을 풀려면 먼저 서버가 어디에 서 있는지부터 알아야 하는데, 웹 서버는 바깥 인터넷과 내부망의 경계에 걸쳐 있습니다. 게시판에 이미지 주소를 넣으면 서버가 그 이미지를 대신 받아 와 미리보기를 만들어 주는 기능이 있다고 하겠습니다. 공격자가 외부 이미지 주소 대신 내부 관리 서버 주소나 백이십칠 점 영 점 영 점 일 같은 서버 자신의 주소를 넣으면, 서버는 그 주소로 요청을 보내고 결과를 보여 줍니다. 바깥에서는 방화벽 때문에 들어갈 수 없는 내부 주소라도, 서버는 내부망 안에 있으므로 접근할 수 있습니다. 즉 공격자는 서버를 대리인으로 삼아 방화벽을 넘는 겁니다.

실기에서는 정의를 주고 이름을 쓰게 하거나, 취약한 코드와 대응을 서술하게 합니다. 실제로 2025년 1회 실기에는 서버가 클라이언트 요청을 통해 내부 네트워크 자원에 접근하게 되는 공격이 무엇이냐는 단답형이 나왔습니다. 에스에스알에프는 몇 회차 뒤에 같은 소재로 다시 출제된 사례도 있습니다.

여기서 지난 편의 씨에스알에프와 헷갈리기 쉽습니다. 씨에스알에프는 사용자의 브라우저가 원치 않는 요청을 보내게 되고, 에스에스알에프는 서버가 원치 않는 요청을 보내게 됩니다. 즉 요청을 위조당하는 주체가 다른 겁니다. 이름은 한 글자 차이지만, 속는 쪽이 사용자냐 서버냐로 갈립니다.


그렇다면 에스에스알에프는 왜 클라우드 환경에서 특히 위험하다고 할까요?

이 궁금증을 풀려면 메타데이터 서비스를 알아야 하는데, 클라우드 가상 서버는 백육십구 점 이백오십사 점 백육십구 점 이백오십사라는 특별한 주소로 자기 자신의 정보를 조회할 수 있습니다. 이를 인스턴스 메타데이터 서비스, 아이엠디에스라고 합니다. 여기에는 서버에 부여된 아이엠 롤의 임시 자격 증명, 즉 클라우드 자원을 조작할 수 있는 키도 들어 있습니다. 공격자가 에스에스알에프로 이 주소의 자격 증명 경로를 요청하게 만들면, 서버가 그 키를 받아 공격자에게 보여 줍니다. 공격자는 그 키로 클라우드의 저장소나 다른 자원에 접근합니다.

그럼 메타데이터 서비스를 아예 꺼야 할까요? 그 대신 나온 방식이 아이엠디에스 버전 투입니다. 버전 원은 겟 요청 한 번이면 바로 정보를 줬습니다. 버전 투는 먼저 풋 요청으로 세션 토큰을 발급받고, 그 토큰을 요청 헤더에 넣어야만 메타데이터를 줍니다. 에스에스알에프 공격자는 대개 주소만 조작할 수 있고 요청 방식이나 헤더는 바꾸기 어려우므로, 버전 투를 강제하면 자격 증명 탈취가 어려워집니다. 기존 실기 문항에 이 서비스의 이름과 역할을 묻는 문제가 있었습니다.


그럼 애플리케이션에서는 에스에스알에프를 어떻게 막아야 할까요?

대응은 서버가 요청할 수 있는 대상을 좁히는 겁니다. 첫째, 요청을 허용할 도메인이나 주소를 화이트리스트로 정합니다. 둘째, 사설 아이피 대역, 루프백 주소인 백이십칠 점 영 점 영 점 일, 메타데이터 주소인 백육십구 점 이백오십사 대역으로 가는 요청을 차단합니다. 셋째, 리다이렉트를 따라가지 않습니다. 외부 주소가 리다이렉트로 내부 주소를 가리키게 하는 우회가 있기 때문입니다. 넷째, 주소를 문자열로만 검사하지 말고, 실제로 해석된 아이피를 기준으로 검사합니다. 같은 주소를 십진수나 다른 표기로 바꿔 필터를 우회하는 방법이 있기 때문입니다. 클라우드 쪽에서는 아이엠디에스 버전 투를 강제하고, 서버에 부여하는 아이엠 롤의 권한을 꼭 필요한 만큼만 줍니다.


그런데 서버가 대신 해 주는 일이 주소 요청만은 아닙니다. 서버가 사용자 입력으로 운영체제 명령까지 대신 실행해 준다면 어떻게 될까요?

관리자 페이지에 아이피를 입력하면 서버가 핑 명령을 실행해 결과를 보여 주는 기능이 있다고 하겠습니다. 코드가 핑 명령 뒤에 입력값을 그대로 붙여 셸에서 실행한다면, 공격자는 아이피 뒤에 세미콜론을 붙이고 캣 슬래시 이티씨 슬래시 패스워드 같은 명령을 이어 씁니다. 세미콜론은 앞 명령이 끝나면 다음 명령을 실행하라는 뜻이므로, 핑 다음에 패스워드 파일을 읽는 명령이 실행됩니다. 세로 막대 기호인 파이프, 앰퍼샌드 두 개, 백틱도 명령을 잇는 데 쓰입니다. 이처럼 외부 입력값이 운영체제 명령의 일부로 실행되어, 공격자가 서버에서 임의의 명령을 실행할 수 있게 되는 취약점을 운영체제 명령어 삽입이라고 합니다.

실기에서는 취약한 코드를 주고 취약점 이름과 보완 방법을 서술하게 합니다. 기존 실기 문항에서는 자바의 런타임 점 익젝으로 외부 입력을 실행하는 코드를 주고, 운영체제 명령어 삽입 취약점과 보완 대책을 쓰게 했습니다.

그럼 어떻게 막을까요? 첫째, 외부 입력을 운영체제 명령으로 직접 실행하지 않도록 설계를 바꿉니다. 가능하면 명령 대신 같은 기능을 하는 라이브러리 함수를 씁니다. 둘째, 꼭 필요하다면 허용할 값만 화이트리스트로 정합니다. 셋째, 세미콜론, 파이프, 앰퍼샌드 같은 명령 연결 문자를 걸러 냅니다. 넷째, 웹 서버 프로세스를 최소 권한으로 실행합니다.


이번에는 첨부 파일을 내려받는 기능을 보겠습니다. 파일 이름만 바꿔서 서버의 다른 파일도 내려받을 수 있을까요?

첨부 파일 다운로드 기능이 다운로드 점 제이에스피 물음표 파일 이퀄 공지 점 피디에프처럼 파일 이름을 파라미터로 받는다고 하겠습니다. 공격자가 파일 값에 점점 슬래시를 여러 번 반복한 뒤 이티씨 슬래시 패스워드를 붙이면, 첨부 파일 폴더에서 최상위 디렉터리까지 올라가 서버의 시스템 파일을 내려받게 됩니다. 이처럼 파일 경로 입력값에 상위 디렉터리를 뜻하는 점 두 개와 슬래시를 넣어 허용된 폴더 밖의 파일에 접근하는 공격을 경로 조작이라고 합니다. 패스 트래버설, 디렉터리 트래버설이라고도 하고, 이렇게 파일을 내려받게 되는 취약점을 파일 다운로드 취약점, 임의 파일 다운로드라고 합니다. 기존 실기 문항에서도 로그를 주고 파일 다운로드 취약점과 조작된 파라미터를 찾게 했습니다.

그렇다면 점점 슬래시라는 글자만 걸러 내면 될까요? 필터를 우회하려고 점과 슬래시를 유알엘 인코딩해서 보내기도 합니다. 슬래시는 퍼센트 이에프, 점은 퍼센트 이이입니다.

대응은 첫째, 파일 이름을 파라미터로 직접 받지 않고 데이터베이스에 저장한 파일 번호로 받는 겁니다. 둘째, 경로를 받아야 한다면 점점 슬래시나 역슬래시 같은 경로 문자를 걸러 냅니다. 셋째, 최종 경로가 정해진 다운로드 폴더 안에 있는지 검사합니다. 1편의 파일 업로드 취약점과는 방향이 반대입니다. 업로드는 공격자의 파일이 서버로 들어오고, 다운로드는 서버의 파일이 밖으로 나갑니다.


그런데 파일을 내려받는 것이 아니라, 불러온 파일을 서버가 실행까지 해 버린다면 어떨까요?

피에이치피 같은 언어는 인클루드나 리콰이어 함수로 다른 파일을 불러와 코드로 실행합니다. 이때 불러올 파일 이름을 외부 입력으로 받아 생기는 취약점을 파일 인클루전이라고 합니다. 예를 들어 페이지 이퀄 메인을 주면 메인 점 피에이치피를 인클루드하는 구조라고 하겠습니다. 공격자가 페이지 값에 점점 슬래시를 붙여 서버 안의 다른 파일, 예를 들어 로그 파일이나 업로드한 파일을 불러오게 하면 로컬 파일 인클루전, 엘에프아이입니다. 페이지 값에 외부 공격자 서버의 주소를 넣어 그곳의 악성 스크립트를 불러오게 하면 리모트 파일 인클루전, 알에프아이입니다.

즉 다운로드는 파일 내용을 내주기만 하지만, 인클루전은 불러온 파일을 코드로 실행하는 겁니다. 그래서 알에프아이는 곧바로 원격 코드 실행으로 이어집니다.

그럼 외부 파일을 못 부르는 엘에프아이는 덜 위험할까요? 그렇지 않습니다. 공격자가 사용자 에이전트 헤더에 피에이치피 코드를 넣어 요청하면 그 코드가 웹 서버 액세스 로그에 기록되고, 엘에프아이로 그 로그 파일을 인클루드하면 기록된 코드가 실행됩니다. 업로드한 이미지 파일 안에 코드를 숨겨 두고 인클루드하는 방법도 같은 원리입니다.

대응은 불러올 파일을 화이트리스트로 정하고, 외부 입력으로 경로를 만들지 않는 겁니다. 그리고 피에이치피 설정 파일인 피에이치피 점 아이엔아이에서 얼라우 유알엘 인클루드와 얼라우 유알엘 에프오픈을 오프로 둡니다. 그러면 외부 주소를 인클루드할 수 없습니다. 기존 실기 문항에 인클루드와 리콰이어, 피에이치피 점 아이엔아이, 오프를 빈칸으로 채우는 문제가 있었습니다.


그렇다면 이 취약점들은 왜 모두 한 편에 묶였을까요?

모두 같은 실수에서 나오기 때문입니다. 사용자가 준 값을 서버가 그대로 믿었다는 겁니다. 에스에스알에프는 주소를, 명령어 삽입은 명령 인자를, 경로 조작은 파일 경로를, 인클루전은 불러올 파일 이름을 믿었습니다. 그래서 서술형 대응에는 세 가지 공통 원칙을 함께 적으면 좋습니다.

첫째, 검증은 반드시 서버에서 합니다. 브라우저의 자바스크립트 검사는 웹 프록시로 쉽게 우회됩니다. 둘째, 막을 값을 나열하는 블랙리스트보다 허용할 값만 정하는 화이트리스트가 안전합니다. 블랙리스트는 인코딩, 대소문자 변형, 새로운 기호로 우회되기 쉽습니다. 셋째, 웹 서버 프로세스에 최소 권한만 줍니다. 취약점이 뚫리더라도 읽을 수 있는 파일과 실행할 수 있는 명령이 줄어들어 피해가 작아집니다.

이 원칙은 지난 편들의 에스큐엘 인젝션, 엑스에스에스, 파일 업로드에도 그대로 적용됩니다. 소프트웨어 개발 보안 가이드에서는 이 취약점들을 모두 입력 데이터 검증 및 표현이라는 같은 유형으로 묶습니다.


정리해 보면, 이미지 주소 하나로 내부 서버를 불러낼 수 있는 이유는 서버가 공격자 대신 내부 주소로 요청을 보내기 때문입니다. 이를 에스에스알에프라고 하고, 씨에스알에프는 브라우저가, 에스에스알에프는 서버가 위조당합니다. 클라우드에서는 아이엠디에스의 자격 증명이 노리는 대상이고, 버전 투는 풋 요청으로 세션 토큰을 먼저 받아야 합니다. 대응은 허용 주소 화이트리스트, 내부 대역과 메타데이터 주소 차단, 리다이렉트 금지입니다. 명령어 삽입은 세미콜론과 파이프로 명령을 잇고, 외부 입력을 명령으로 직접 실행하지 않는 것이 대응입니다. 경로 조작은 점점 슬래시로 상위 폴더에 올라가고, 파일 번호로 받고 경로 문자를 걸러 냅니다. 엘에프아이는 서버 안의 파일을, 알에프아이는 외부 파일을 인클루드해 실행하며, 얼라우 유알엘 인클루드와 에프오픈을 오프로 둡니다. 공통 원칙은 서버 측 검증, 화이트리스트, 최소 권한입니다.
