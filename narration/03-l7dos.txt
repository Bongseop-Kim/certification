정보보안기사 실기 궁금증 3편. 트래픽은 적은데, 웹 서버는 왜 쓰러졌을까?

그런데 정말 회선을 채우지도 않는 적은 트래픽으로 웹 서버를 쓰러뜨릴 수 있을까요?

이 궁금증을 풀려면 먼저 네트워크 계층 공격과 무엇이 다른지 알아야 하는데, 가장 큰 차이는 세 번 악수를 정상적으로 마친 진짜 연결을 쓴다는 점입니다. 출발지 주소를 위조하지 않으므로 신 쿠키 같은 대응으로는 걸러지지 않습니다. 회선 사용량도 평소와 크게 다르지 않아서, 회선 모니터링만 보면 공격을 놓치기 쉽습니다. 반면 웹 서버는 요청 하나를 처리할 때마다 프로세스나 스레드, 데이터베이스 조회 같은 비싼 자원을 씁니다. 즉 적은 양으로도 웹 서버는 쉽게 지치는 겁니다.

응용 계층 공격은 두 갈래로 나눌 수 있습니다. 첫째, 요청의 양으로 밀어붙이는 공격입니다. 겟 플러딩과 씨씨 어택이 여기에 속합니다. 둘째, 요청의 속도를 늦춰 연결을 오래 붙잡는 공격입니다. 슬로로리스, 슬로 에이치티티피 포스트, 슬로 에이치티티피 리드가 여기에 속합니다.


그럼 먼저 양으로 밀어붙이는 공격은 어떤 모습일까요?

봇넷에 감염된 다수의 컴퓨터가 정상적인 겟 요청을 대량으로 보내 웹 서버의 자원을 고갈시키는 공격을 에이치티티피 겟 플러딩이라고 합니다. 요청 하나하나는 완전히 정상입니다. 메인 페이지나 검색 페이지처럼 처리 부담이 큰 주소를 반복해서 요청합니다. 액세스 로그를 보면 같은 주소에 대한 겟 요청이 초당 수천 건 쌓이고, 출발지 아이피는 수백 개로 흩어져 있습니다.

그렇다면 정상 요청과 똑같이 생긴 공격은 어떻게 걸러 낼까요? 내용이 아니라 양으로 걸러야 합니다. 대응의 핵심은 아이피 하나가 일정 시간 동안 보내는 요청 수에 임계값을 두고, 넘으면 차단하는 겁니다. 사람이 브라우저로는 낼 수 없는 속도이기 때문입니다. 또 자동화 도구는 쿠키나 자바스크립트를 제대로 처리하지 못하는 경우가 많아서, 처음 접속할 때 간단한 확인 절차를 거치게 하는 방법도 씁니다.

여기서 지난 편의 신 플러딩과 헷갈리기 쉽습니다. 신 플러딩은 연결을 완성하지 않고 대기 큐를 채우므로 신 리시브드 상태가 많습니다. 겟 플러딩은 연결을 완성한 뒤 요청을 쏟아내므로 이스태블리시드 상태와 액세스 로그가 함께 늘어납니다.


그런데 큰 웹 서비스는 원본 서버 앞에 캐시 서버를 둡니다. 자주 요청되는 페이지는 캐시 서버가 저장해 둔 사본으로 대신 응답해서 원본 서버의 부담을 줄입니다. 그렇다면 캐시 서버가 있는 곳에는 겟 플러딩이 통하지 않을까요?

실기에서는 요청 헤더를 보여 주고 어떤 공격인지 묻습니다. 겟 요청이 대량인데 헤더에 캐시 컨트롤 노 캐시가 붙어 있다면 씨씨 어택입니다. 기존 실기 문항에서도 씨씨 어택이 단답 정답으로 나왔습니다. 대응은 캐시 컨트롤 노 캐시가 붙은 요청이 짧은 시간에 몰리면 해당 아이피를 차단하는 겁니다.


그럼 이번에는 반대로, 요청 수가 적은데도 서버가 멈추는 경우는 어떻게 설명할 수 있을까요?

이 궁금증을 풀려면 에이치티티피 요청의 구조부터 알아야 하는데, 요청은 요청 줄과 헤더, 그리고 바디로 구성됩니다. 헤더 각 줄은 캐리지 리턴과 라인 피드로 끝나고, 헤더가 모두 끝났다는 표시로 빈 줄 하나가 옵니다. 즉 캐리지 리턴 라인 피드가 두 번 연속으로 오면 헤더가 끝나고 바디가 시작됩니다. 글자로는 백슬래시 알 백슬래시 엔을 두 번 쓴 모양입니다.

그런데 이 빈 줄을 절대 보내지 않으면 어떻게 될까요? 공격자는 의미 없는 헤더를 한 줄씩, 수십 초 간격으로 아주 천천히 계속 보냅니다. 웹 서버는 헤더가 끝나지 않았으니 연결을 끊지 못하고 기다립니다. 이런 연결 수백 개면 웹 서버의 동시 접속 처리 슬롯이 모두 막혀 새 사용자를 받지 못합니다. 이를 슬로로리스라고 합니다. 이름은 느린 동물인 늘보원숭이, 슬로로리스에서 따왔고, 공식적인 분류 이름으로는 슬로 에이치티티피 헤더 도스라고 부릅니다.

기존 실기 문항에서는 에이치티티피 헤더의 끝을 알리는 개행 문자를 완성하지 않고 불완전한 헤더를 계속 보내 연결 자원을 점유하는 공격으로 정의했습니다. 헤더 끝을 알리는 두 문자, 캐리지 리턴과 라인 피드, 시알과 엘에프를 빈칸으로 묻는 문제도 있었습니다. 같은 두 문자는 에이치티티피 응답 분할 공격에서도 헤더를 끊는 데 악용됩니다.

그렇다면 헤더는 정상적으로 끝내면 안전할까요? 그렇지 않습니다. 포스트 요청은 헤더의 콘텐츠 렝스 항목에 바디의 길이를 적고, 웹 서버는 그 길이만큼 바디를 모두 받을 때까지 연결을 유지합니다. 공격자는 콘텐츠 렝스를 아주 크게 적어 놓고, 바디를 몇 초에 한 바이트씩 보냅니다. 서버는 끝까지 기다릴 수밖에 없고, 연결은 오래 붙잡힙니다. 이를 슬로 에이치티티피 포스트라고 하고, 루디라는 도구 이름으로도 부릅니다. 즉 슬로로리스는 헤더를 끝내지 않고, 슬로 포스트는 헤더는 끝내되 바디를 늦추는 겁니다.

그럼 요청을 정상으로 다 보내면 이제 안전할까요? 이번에는 방향이 반대인 공격이 있습니다. 요청은 정상으로 보내고, 응답을 받는 쪽에서 시간을 끄는 겁니다. 티씨피에는 윈도우 크기라는 값이 있는데, 받는 쪽이 지금 받을 수 있는 데이터의 양을 상대에게 알려 주는 값입니다. 공격자는 정상 연결을 맺은 뒤 윈도우 크기를 영으로 알립니다. 받을 공간이 없다는 뜻이므로 서버는 응답을 보내지 못하고 공간이 생길 때까지 기다립니다. 그동안 연결과 응답 데이터가 서버 자원을 계속 차지합니다. 이를 슬로 에이치티티피 리드라고 합니다. 기존 실기 문항에서도 정상적인 연결을 맺은 뒤 윈도우 크기를 영으로 조작해 서버가 응답 데이터를 보내지 못하고 대기하게 만드는 공격으로 정리되어 있습니다. 패킷 분석 문제에서 윈도우 크기 영이 반복해서 보이면 슬로 리드를 떠올리면 됩니다.

정리하면 슬로로리스는 헤더를, 슬로 포스트는 바디를, 슬로 리드는 응답 수신을 늦춥니다. 공통점은 트래픽은 적지만 연결을 오래 붙잡는다는 겁니다.


그런데 교재에는 이름이 비슷하지만 원리가 조금 다른 응용 계층 공격이 두 가지 더 나옵니다. 이건 또 무엇일까요?

하나는 해시 도스입니다. 웹 서버는 요청 파라미터를 해시 테이블에 저장하는데, 해시 테이블은 보통 매우 빠르지만 해시 값이 같은 키가 많이 들어오면 충돌을 처리하느라 급격히 느려집니다. 공격자는 해시 값이 서로 충돌하도록 고른 파라미터 수천, 수만 개를 포스트 요청 하나에 담아 보냅니다. 요청 몇 개만으로도 서버의 시피유 사용률이 치솟습니다. 대응은 요청 하나에 들어올 수 있는 파라미터 개수와 바디 크기를 제한하는 겁니다.

다른 하나는 헐크 도스입니다. 겟 플러딩을 변형한 공격인데, 같은 주소를 반복해서 요청하면 임계값 차단이나 캐시에 쉽게 걸리므로, 요청할 때마다 주소 뒤의 파라미터 값을 무작위로 바꿔 매번 다른 주소처럼 보이게 합니다. 사용자 에이전트와 리퍼러 같은 헤더도 바꿔 가며 보냅니다. 그래서 같은 주소 기준이 아니라 아이피 기준으로 요청 수를 세어 차단하는 것이 대응입니다.


그렇다면 슬로 계열 공격은 웹 서버 설정으로 어떻게 막을 수 있을까요?

슬로 계열 공격은 웹 서버가 기다려 주는 시간을 이용하므로, 기다림에 한계를 두는 것이 대응의 핵심입니다.

첫째, 타임아웃 값을 줄입니다. 아파치의 타임아웃 지시어는 요청을 받거나 응답을 보낼 때 기다리는 최대 시간입니다. 길게 잡혀 있으면 느린 연결이 오래 버팁니다. 리퀘스트 리드 타임아웃 모듈을 쓰면 헤더를 받는 시간과 바디를 받는 시간을 따로, 그리고 최소 전송 속도까지 정할 수 있어 슬로로리스와 슬로 포스트에 효과적입니다.

둘째, 리밋 리퀘스트 바디로 요청 바디의 최대 크기를 제한합니다. 콘텐츠 렝스를 터무니없이 크게 잡는 슬로 포스트를 막고, 큰 파일 업로드로 서버를 괴롭히는 것도 막습니다. 기존 실기 문항에서 업로드되는 최대 용량을 설정하는 지시어로 리밋 리퀘스트 바디가 나왔습니다.

셋째, 아이피 하나가 동시에 맺을 수 있는 연결 수를 제한합니다. 슬로 공격은 한 곳에서 연결을 많이 붙잡는 방식이라 효과가 큽니다.

넷째, 킵 얼라이브 시간을 짧게 잡아 요청이 끝난 연결이 오래 남아 있지 않게 합니다.


그럼 실제 시험에서 로그 한 장을 받았을 때, 어떤 공격인지는 어떻게 구분할까요?

실기 실무형에서는 로그나 넷스탯 결과를 주고 공격을 구분하게 합니다. 두 가지를 같이 보면 됩니다. 액세스 로그의 요청 수, 그리고 연결 상태입니다. 겟 플러딩과 씨씨 어택은 요청 수가 폭증합니다. 액세스 로그가 빠르게 쌓이고, 같은 주소를 반복해서 요청합니다. 씨씨 어택이라면 요청 헤더에 캐시 컨트롤 노 캐시가 붙어 있습니다. 슬로 계열은 반대로 요청 수가 적습니다. 대신 이스태블리시드 상태 연결이 몇몇 아이피에 몰려 오래 유지됩니다. 요청이 끝나지 않으니 액세스 로그에는 오히려 잘 드러나지 않습니다. 즉 로그가 조용하다고 해서 공격이 없다고 단정할 수는 없는 겁니다. 요청 수와 연결 상태, 이 두 가지를 함께 놓고 봐야 양으로 미는 공격과 시간을 끄는 공격이 갈립니다.

네트워크 계층 공격과도 구분해 둡니다. 신 리시브드 상태가 많으면 신 플러딩, 회선 사용량 자체가 꽉 찼다면 유디피 플러딩이나 증폭 공격입니다. 대응도 다릅니다. 회선 공격은 회선 업체와 블랙홀 라우팅으로, 응용 계층 공격은 웹 서버 설정과 아이피별 임계값으로 막습니다.


정리해 보면, 응용 계층 디도스는 정상 연결로 웹 서버의 비싼 자원을 노리기 때문에 신 쿠키로는 막을 수 없습니다. 겟 플러딩은 정상 겟 요청을 대량으로 보내고, 대응은 아이피별 요청 수 임계값입니다. 씨씨 어택은 캐시 컨트롤 노 캐시로 캐시 서버를 우회해 원본 서버에 부하를 줍니다. 슬로로리스는 헤더 끝 빈 줄, 시알 엘에프 두 번을 보내지 않고, 슬로 포스트는 콘텐츠 렝스를 크게 잡고 바디를 천천히 보내며, 슬로 리드는 윈도우 크기를 영으로 알립니다. 해시 도스는 충돌하는 파라미터로 시피유를 소모시키고, 헐크 도스는 매번 다른 주소로 겟 플러딩을 합니다. 설정으로는 타임아웃 단축, 리퀘스트 리드 타임아웃, 리밋 리퀘스트 바디, 아이피별 동시 연결 제한으로 막습니다. 요청이 폭증하면 겟 플러딩과 씨씨 어택, 요청은 적은데 연결이 오래 붙어 있으면 슬로 계열입니다.
