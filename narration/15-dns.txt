정보보안기사 실기 궁금증 15편. 주소를 정확히 쳤는데, 왜 가짜 은행 사이트가 열릴까?

우리는 인터넷 사이트에 접속할 때 숫자로 된 아이피 주소 대신 도메인 이름을 입력합니다. 컴퓨터는 이 이름을 아이피 주소로 바꿔야 실제로 접속할 수 있는데, 이 일을 해 주는 시스템을 디엔에스, 도메인 네임 시스템이라고 합니다. 디엔에스는 최근 실기에서 거의 매년 한 문제씩 나오는 반복 소재이고, 설정 파일 이름이나 지시어를 빈칸으로 묻는 경우가 많아서 철자까지 정확히 기억해 두는 것이 중요합니다.

그런데 정말 은행 주소를 한 글자도 틀리지 않고 입력했는데 가짜 사이트로 갈 수 있을까요?

이 궁금증을 풀려면 먼저 이름이 아이피로 바뀌는 과정부터 알아야 하는데, 디엔에스 서버는 역할에 따라 두 가지로 나뉩니다. 재귀 디엔에스는 사용자의 질의를 받아서, 답을 모르면 사용자 대신 끝까지 찾아다니는 서버입니다. 통신사나 회사 내부에서 운영하는 디엔에스 서버가 보통 여기에 해당합니다. 권한 디엔에스는 특정 도메인의 원본 레코드를 직접 가지고 있어서, 그 도메인에 대해 최종 정답을 줄 수 있는 서버입니다.

사용자가 더블유 더블유 더블유 점 예시 점 컴을 물으면, 재귀 서버는 먼저 루트 서버에 묻습니다. 루트 서버는 점 컴을 담당하는 최상위 도메인 서버를 알려 줍니다. 재귀 서버는 다시 최상위 도메인 서버에 묻고, 예시 점 컴을 관리하는 권한 서버의 위치를 받습니다. 마지막으로 권한 서버에 물어 아이피를 받아 사용자에게 돌려줍니다.

그렇다면 이 과정에서 질의 방식은 모두 같을까요? 그렇지 않습니다. 사용자가 재귀 서버에 보내는 질의는 끝까지 찾아서 답을 달라는 재귀 질의입니다. 반면 재귀 서버가 루트, 최상위 도메인, 권한 서버를 차례로 찾아가는 과정은, 각 서버가 다음에 물어볼 곳만 알려 주는 반복 질의입니다. 실기에서는 두 서버의 설명을 주고 이름을 빈칸으로 묻는 단답형이 나옵니다. 대신 찾아 준다는 말이 있으면 재귀 디엔에스, 원본 레코드나 정답이라는 말이 있으면 권한 디엔에스입니다.


그런데 컴퓨터는 정말 매번 디엔에스 서버에 물어볼까요?

아닙니다. 컴퓨터는 디엔에스 서버에 묻기 전에 먼저 자기 안을 확인합니다. 호스트 파일과 디엔에스 캐시입니다. 호스트 파일은 도메인과 아이피를 직접 짝지어 적어 둔 텍스트 파일입니다. 리눅스에서는 슬래시 이티씨 슬래시 호스트, 윈도우에서는 시스템 폴더 아래 드라이버스 슬래시 이티씨 폴더에 있습니다. 여기에 적힌 도메인은 디엔에스 서버에 묻지도 않고 적힌 아이피로 바로 갑니다. 윈도우는 시작할 때 호스트 파일 내용을 디엔에스 캐시에 미리 올려 두기도 합니다.

바로 이 특성을 악용한 공격이 파밍입니다. 악성코드가 피해자 컴퓨터의 호스트 파일에 은행 도메인과 공격자 서버 아이피를 한 줄 써 넣습니다. 그러면 사용자가 주소창에 정확한 도메인을 입력해도 가짜 사이트로 갑니다. 즉 주소를 정확히 쳤는데도 가짜 사이트가 열린 건, 디엔에스 서버에 묻기도 전에 내 컴퓨터 안에서 답이 정해졌기 때문인 겁니다. 주소창의 주소는 진짜처럼 보이니 사용자가 알아채기도 어렵습니다.

윈도우에는 하나 더 기억할 파일이 있습니다. 인터넷 연결 공유 기능을 켜면 생기는 호스트 점 아이씨에스 파일입니다. 이 파일은 일반 호스트 파일보다 먼저 적용될 수 있어서, 파밍 점검 때 함께 확인해야 합니다. 기존 실기 문제에 이 파일 이름이 그대로 답으로 나왔습니다.

대응은 호스트 파일을 정기적으로 점검하고, 일반 사용자가 수정하지 못하도록 권한을 제한하며, 백신으로 변조를 탐지하는 것입니다.


그렇다면 디엔에스 서버 쪽에서는 어떤 일이 벌어질 수 있을까요?

디엔에스 서버는 한 번 찾은 답을 일정 시간 저장해 둡니다. 이를 디엔에스 캐싱이라고 합니다. 같은 질문이 다시 오면 상위 서버에 묻지 않고 저장된 답을 바로 돌려줍니다. 응답이 빨라지고, 루트 서버와 상위 서버에 가는 반복 질의 부하가 줄어듭니다.

그럼 저장된 답은 영원히 유지될까요? 레코드마다 티티엘, 타임 투 리브라는 유지 시간이 붙어 있고, 이 시간이 지나면 캐시에서 지우고 다시 물어봅니다. 티티엘은 권한 서버 관리자가 레코드를 등록할 때 정합니다. 티티엘이 길면 부하는 줄지만 아이피를 바꿨을 때 반영이 늦고, 짧으면 반영은 빠르지만 질의가 늘어납니다.

실제로 2025년 2회 실기에는 이 내용이 빈칸으로 나왔습니다. 디엔에스가 쓰는 전송 계층 프로토콜, 반복 질의 부하를 줄이는 저장 기능, 그 정보의 유지 시간을 차례로 물었고, 답은 유디피, 디엔에스 캐싱, 티티엘이었습니다.

캐시는 편리하지만 공격 대상이 되기도 합니다. 캐시에 잘못된 답이 한 번 들어가면 티티엘 동안 그 서버를 쓰는 모든 사용자가 잘못된 답을 받게 되니까요.


그럼 공격자는 어떻게 가짜 답을 끼워 넣을까요?

위조된 디엔에스 응답으로 사용자를 가짜 사이트로 보내는 공격을 넓게 디엔에스 스푸핑이라고 합니다. 대표적인 방식은 같은 네트워크에서 피해자의 디엔에스 질의를 엿보다가, 진짜 디엔에스 서버보다 먼저 위조 응답을 보내는 것입니다. 피해자 컴퓨터는 먼저 도착한 응답을 믿고 공격자가 지정한 아이피로 접속합니다. 그래서 디엔에스 스푸핑은 에이알피 스푸핑 같은 중간자 공격과 함께 쓰이는 경우가 많습니다.

디엔에스 캐시 포이즈닝은 그중에서도 디엔에스 서버의 캐시를 오염시키는 공격입니다. 재귀 서버가 권한 서버에 질의를 보내면, 공격자는 진짜 응답이 오기 전에 위조 응답을 대량으로 보냅니다. 디엔에스 응답에는 질의와 짝을 맞추는 트랜잭션 아이디가 있는데, 이 값을 맞힌 위조 응답이 먼저 도착하면 재귀 서버는 그것을 진짜로 믿고 캐시에 저장합니다. 그 뒤로는 티티엘 동안 그 서버를 쓰는 모든 사람이 가짜 사이트로 갑니다.

즉 두 공격의 차이는 피해 범위인 겁니다. 스푸핑은 주로 개별 사용자를 속이고, 캐시 포이즈닝은 서버를 오염시켜 다수를 한꺼번에 속입니다. 실기에서는 설명을 주고 공격 이름을 묻는데, 서버의 캐시를 오염시킨다는 말이 있으면 캐시 포이즈닝, 사용자에게 위조 응답을 보낸다는 말이 중심이면 디엔에스 스푸핑으로 답합니다.

대응은 재귀 질의를 내부 사용자에게만 허용하고, 질의할 때 출발 포트와 트랜잭션 아이디를 무작위로 바꿔 맞히기 어렵게 하며, 근본적으로는 디엔에스섹으로 응답의 진위를 검증하는 것입니다.


그렇다면 디엔에스는 어떤 포트와 프로토콜을 쓸까요?

디엔에스는 오십삼번 포트를 씁니다. 평소의 질의와 응답은 빠른 유디피 오십삼번으로 처리합니다. 그런데 응답 데이터가 오백십이 바이트를 넘으면, 서버는 잘렸다는 표시를 붙여 응답하고 클라이언트는 티씨피 오십삼번으로 다시 질의합니다. 서버끼리 영역 데이터 전체를 복사하는 영역 전송도 신뢰성이 필요하므로 티씨피 오십삼번을 씁니다.

즉 디엔에스가 유디피만 쓴다고 단정하는 것은 틀린 겁니다. 기본은 유디피이지만 큰 응답과 영역 전송에는 티씨피를 씁니다. 디엔에스는 티씨피와 유디피를 모두 쓴다는 문장은 맞는 문장입니다. 실기에서는 디엔에스의 전송 계층 프로토콜을 묻는 단답형과, 유디피와 티씨피를 각각 언제 쓰는지 서술하는 문제가 나옵니다. 방화벽 정책을 보는 실무형에서도 디엔에스 질의를 막으려면 유디피 오십삼번을 차단한다는 판단을 요구합니다.


그런데 방금 나온 영역 전송은 무엇이고, 왜 위험할까요?

영역 전송, 존 트랜스퍼는 주 디엔에스 서버의 영역 파일 전체를 보조 디엔에스 서버로 복사하는 기능입니다. 주 서버가 장애를 일으켜도 보조 서버가 같은 답을 줄 수 있게 하려는 겁니다.

문제는 이 기능을 아무에게나 허용했을 때입니다. 공격자가 영역 전송을 요청하면 그 도메인에 등록된 모든 호스트 이름과 아이피 목록을 한 번에 가져갈 수 있습니다. 내부 서버 이름, 관리 서버, 테스트 서버까지 드러나기 때문에 공격 전 정찰에 매우 유용한 자료가 됩니다. 정찰 도구로는 엔에스룩업이나 디그 명령이 쓰입니다.

대응은 영역 전송을 허용된 보조 서버로만 제한하는 것입니다. 디엔에스 서버 프로그램인 바인드에서는 설정 파일 네임드 점 콘프의 옵션 안에 얼라우 트랜스퍼 항목을 넣고, 중괄호 안에 보조 서버 아이피만 적습니다. 보조 서버가 없다면 논이라고 적어 아무에게도 허용하지 않습니다. 실기에서는 영역 전송을 제한하는 지시어를 빈칸으로 묻는 단답형이 여러 번 나왔고, 답은 얼라우 트랜스퍼였습니다. 비슷한 지시어로 질의를 허용할 대상을 정하는 얼라우 쿼리, 재귀 질의를 허용할 대상을 정하는 얼라우 리커전도 함께 구분해 두면 좋습니다.


그럼 리눅스에서 디엔에스 설정은 어느 파일에 적을까요?

두 개를 짝으로 기억합니다. 네임드 점 콘프는 바인드의 설정 파일입니다. 영역 정보, 영역 전송 허용 대상, 재귀 허용 여부 같은 서버 동작을 정합니다. 리졸브 점 콘프는 슬래시 이티씨 아래에 있고, 이 시스템이 질의할 때 어느 디엔에스 서버를 쓸지 네임서버 줄로 지정하는 파일입니다. 도메인 검색 규칙도 여기에 적습니다. 즉 네임드 점 콘프는 답하는 쪽의 설정, 리졸브 점 콘프는 묻는 쪽의 설정인 겁니다.

실제로 2026년 2회 실기에는 이 두 파일 이름이 빈칸으로 나왔습니다. 한 수험생은 리졸브 뒤에 이를 붙여 써서 틀렸다고 복원 글에 남겼습니다. 철자를 정확히 기억해 두세요. 알 이 에스 오 엘 브이, 리졸브입니다.

서버 설정에서 함께 챙길 항목도 있습니다. 외부 누구에게나 재귀 질의를 해 주는 열린 재귀 서버는 캐시 포이즈닝과 디엔에스 증폭 공격에 악용됩니다. 그래서 외부에 공개하는 권한 서버라면 리커전 노로 재귀 기능을 끄고, 내부용 재귀 서버라면 얼라우 리커전으로 내부 대역에만 허용합니다. 버전 정보도 노출하지 않도록 설정합니다.


그렇다면 받은 응답이 진짜인지 확인할 방법은 없을까요?

캐시 포이즈닝이 가능했던 근본 이유는 받은 응답이 정말 권한 서버에서 왔는지 확인할 방법이 없었기 때문입니다. 이를 보완한 보안 확장이 디엔에스섹입니다. 권한 서버가 레코드에 전자서명을 붙이고, 받는 쪽이 공개키로 그 서명을 검증합니다. 공개키 자체도 상위 영역의 서명으로 연결되어 루트까지 이어지는 신뢰 사슬을 만들고, 위조된 응답은 서명 검증에서 걸러집니다.

그런데 디엔에스섹을 쓰면 디엔에스 내용도 숨겨질까요? 그렇지 않습니다. 실기에서 가장 많이 나오는 함정이 바로 기밀성입니다. 디엔에스섹은 무결성과 출처 인증을 제공하지만 기밀성은 제공하지 않습니다. 질의와 응답 내용은 암호화되지 않고 그대로 보입니다. 보기 중에 디엔에스섹이 디엔에스 데이터를 암호화한다는 문장이 있으면 틀린 문장입니다.

마지막으로 디엔에스 사고 대응 순서입니다. 감염된 사용자 컴퓨터의 호스트 파일을 복구하고, 오염된 재귀 서버의 캐시를 비웁니다. 윈도우 사용자 컴퓨터에서는 아이피컨피그 슬래시 플러시디엔에스 명령으로 캐시를 지웁니다. 재귀 질의는 내부 대역에만 허용하고, 영역 전송은 보조 서버로 제한하고, 디엔에스섹을 적용합니다.


정리해 보면, 재귀 디엔에스는 대신 끝까지 찾아 주는 서버, 권한 디엔에스는 원본 레코드를 가진 서버입니다. 컴퓨터는 호스트 파일과 캐시를 먼저 보기 때문에 호스트 파일을 바꾸는 파밍에 당하면 정확한 주소로도 가짜 사이트에 갑니다. 윈도우 인터넷 연결 공유에서는 호스트 점 아이씨에스도 확인합니다. 디엔에스 캐싱은 답을 저장해 부하를 줄이고, 티티엘은 그 유지 시간입니다. 디엔에스 스푸핑은 위조 응답으로 사용자를 속이고, 캐시 포이즈닝은 서버 캐시를 오염시켜 다수를 속입니다. 디엔에스는 유디피 오십삼번이 기본이고, 오백십이 바이트 초과와 영역 전송은 티씨피 오십삼번입니다. 영역 전송 제한은 얼라우 트랜스퍼, 재귀 제한은 리커전 노와 얼라우 리커전입니다. 네임드 점 콘프는 바인드 서버 설정, 리졸브 점 콘프는 네임서버 지정입니다. 디엔에스섹은 전자서명으로 무결성과 출처 인증을 주지만 기밀성은 없습니다.
