# 실기 교재 텍스트 추출 및 문제 데이터화 계획

작성: 2026-10-02. 상태: 계획 작성. 전체 추출·문제 등록·사이트 변경은 아직 시작하지 않았다.

## 목표와 범위

현재 전자책 뷰어에서 열려 있는 『2026 정보보안기사 실기 기출 600제』의 전체 페이지를 순회하여 접근성 정보에서 읽히는 텍스트를 저장하고, 문제·지문·소문항·정답·해설을 구조화한다. 사용자가 만든 사이트에서 실기 문제를 풀 수 있게 하는 것이 목적이다.

책 제목의 ‘600제’를 등록 수량 목표로 삼지 않는다. 전체 페이지의 처리 여부는 추출 범위 확인에 사용하고, 앱에 등록할 문항은 독립적으로 검수한다. 목차·머리말·해설도 원본 추출에는 포함하되 문제로 등록하지 않는다.

## 확인한 사실과 제약

- `cua_repl`에서 `전자책 뷰어 앱`을 지정하면 책 본문을 읽을 수 있다. bundle ID는 설치본과 마운트된 설치 이미지가 겹쳐 모호했다.
- 화면 캡처는 흰색으로 나왔지만 접근성 트리에는 본문·정답·해설이 있었다. 이미지 캡처나 OCR 없이 텍스트 읽기를 우선한다.
- 뷰어의 총 페이지 표시는 442였다. 추출 시작 때 다시 확인한다. PDF 페이지, 인쇄 페이지, 문항 번호는 서로 다른 값으로 기록한다.
- 현재 접근성 트리는 인접 페이지를 함께 반환한다. 트리의 `showing 73-75 of 100 items` 같은 표시는 전체 페이지 수나 교재 문항 번호로 해석하지 않는다.
- 073번 문항은 온전히 읽혔으나 074번에는 문장 중복·누락이 있었다. 이전 080번에서는 질문 제목과 본문 주제가 불일치했다. 접근성 텍스트만으로 원문 오류와 추출 오류를 구분할 수 없다.
- 그림·네트워크 구성도·일부 표의 관계는 텍스트만으로 복원되지 않을 수 있다. 이를 추측해 채우지 않는다.
- 앱의 `Question`은 `mc | short`만 지원하고, 단답은 문자열 하나를 정규화해 비교한다. 서술형·복수 정답을 단답으로 억지로 넣으면 잘못 채점된다.
- `AGENTS.md`에 적힌 `scripts/short/cards_<subject>.py`, `scripts/short/build.py`는 현재 체크아웃에 없다. 기존 문서의 완료 기록을 구현 현황으로 간주하지 않는다.

## 1. 먼저 한 페이지로 저장·이동을 검증한다

1. 앱을 경로로 선택하고 전체 접근성 트리를 읽는다.
2. 현재 페이지 입력 필드를 최신 트리에서 찾는다. 기존에 관찰한 숫자 인덱스를 재사용하지 않는다.
3. 페이지 번호를 입력하고 Return으로 이동한 뒤, 새 트리에서 페이지 값과 본문이 바뀌었는지 확인한다.
4. 반환 텍스트를 로컬 파일에 실제 저장할 수 있는지 확인한다. 도구 출력에 보였다는 것만으로 저장 성공으로 판단하지 않는다.
5. 같은 페이지를 다시 읽어 문항 경계·정답·해설이 재현되는지 비교한다. 이동 전 페이지로 복귀한다.

저장 경로가 검증된 다음 전체 순회를 시작한다. `cua_repl`의 실제 지원 API만 사용하고, 읽기 결과를 파일에 전달하는 방법이 없다면 먼저 그 구체적인 제약을 해결한다. 새로운 캡처 프로그램 설치나 DRM 변경을 전제로 하지 않는다.

## 2. 페이지별 원본을 저장한다

예정 경로:

```text
scripts/ebook/practical-2026/
  raw/0001.txt             # 전체 접근성 트리, 원문 그대로
  manifest.json           # 페이지별 처리 상태·재시도·해시
  questions.json          # 구조화한 교재 문항
  review.md               # 누락·표·그림·정답 불일치 검수 목록
```

- 한 번에 한 페이지씩 이동 → 관찰 → 저장한다. 같은 앱을 여러 작업자가 동시에 조작하지 않는다.
- 원본 트리는 수정하지 않고 UTF-8로 보존한다. manifest에는 목표 PDF 페이지, 실제 표시 값, 저장 파일, 관찰 시각, 내용 해시와 오류를 남긴다.
- 실제 페이지 값이 목표와 다르거나 본문이 이전 페이지와 같으면 성공 처리하지 않는다. 재관찰 후에도 해결되지 않으면 실패 상태와 이유를 남긴다.
- 페이지마다 저장을 완료한 후 다음 페이지로 넘어간다. 중단되면 manifest의 미처리·실패 페이지부터 재개한다.
- 해시는 반복 캡처 감지용이다. 같은 텍스트라는 이유로 서로 다른 페이지를 자동 삭제하지 않는다.
- 인접 페이지 중복은 구조화 단계에서 합친다. 원본 파일을 지우지 않는다.
- 도구 호출·저장·검수는 작은 묶음으로 진행해 중간 결과를 확인한다. 전체 순회를 한 번의 긴 UI 루프로 실행하지 않는다.
- 책 전체의 원본과 구조화 데이터는 로컬에 보존한다. 웹에 번들되는 경로는 검수한 풀이 데이터만 대상으로 한다.

## 3. 원문 구조를 보존하며 문항을 나눈다

`문항 번호 → 질문/지문 → 소문항 → 정답 & 해설 → 다음 문항`을 경계로 사용한다. 문항 번호만으로 분리하지 않고 절·회차·페이지 문맥을 함께 본다. 책 안에서 문항 번호가 재시작될 수 있다.

구조화 데이터 예시(필드 구조를 설명하는 예이며, 실제 문항 등록 아님):

```json
{
  "id": "practical-2026:section-01:q073",
  "section": "section-01",
  "originalNo": "073",
  "pdfPages": [73],
  "printedPages": [],
  "kind": "term",
  "body": "검수한 질문",
  "stimulus": null,
  "parts": [],
  "answerText": "교재 정답 원문",
  "explanation": "교재 해설 원문",
  "rawFiles": ["raw/0073.txt"],
  "status": "needs-review",
  "issues": []
}
```

`pdfPages` 예시 값은 실제 위치 검증 전까지 근거로 쓰지 않는다. 소문항은 `parts`에 번호·질문·대응 정답을 기록하고, 표·코드는 행/열과 줄바꿈을 유지한다. `kind`는 용어 단답·복수 빈칸·서술·계산·선택 등 관찰한 형식을 표시한다.

줄바꿈·머리말·UI 문자열 제거는 정리본에서만 한다. 같은 정답이 정답란과 해설 제목에 반복되는 것은 구조상 반복일 수 있어 무조건 삭제하지 않는다. 이어지는 페이지의 문항을 합칠 때는 출처 페이지를 모두 유지한다.

누락된 문장, 깨진 표, 그림 의존 문제, 정답과 질문의 불일치는 `issues`와 `review.md`에 기록한다. 지식으로 원문을 추정해 복원하지 않는다. 재관찰·공식 정오표·사용자가 확인한 원문으로 해결하고, 교재 자체 오류 수정은 원문과 수정 이유를 모두 보존한다.

## 4. 검수 후 사이트용으로 분리한다

### 교재 전체: 별도 실기 데이터와 풀이 모드

검수한 교재 문항은 `questions/practical/practical-2026.json`에 내보낸다. 기존 `questions/written` glob에 섞지 않아 필기 모의고사·단답 암기 풀에 서술형이 유입되지 않게 한다.

최소 실기 모드는 문제/지문/소문항 표시 → 답안 입력 → 정답·해설 공개 → 사용자 정답/오답 판단 → 다음 문제로 구성한다. 서술형과 복수 빈칸은 모델 답안과 비교하는 자가 채점을 기본으로 한다. 임의의 키워드 일치나 AI 채점으로 정답을 단정하지 않는다. 답안 입력 중 정답이 노출되지 않도록 분리한다.

기존 풀이 기록의 `question_key`, `chosen`, `correct` 구조를 재사용할 수 있는지 확인하고, 공통 조회·복습·결과 화면의 `byKey`와 모드 처리를 함께 점검한다. DB 스키마 변경은 실제 필요한 경우에만 한다. 원문에서 읽히지 않은 문항은 풀이 목록에 넣지 않고 보류 내역으로 남긴다.

### 기존 단답 풀: 조건을 만족하는 문항만

- 설명 → 용어·약어·숫자 하나인 경우만 후보로 삼는다. 복수 빈칸은 각각 독립적으로 답할 수 있을 때만 한 값씩 분리한다.
- 기존 필기 단답 풀에 넣으려면 교재 수록 사실 외에 기출 정답 보기·복수 회차 반복·출제기준 중 하나의 선정 근거가 필요하다. 실기 교재 전체를 필기 단답으로 바꾸지 않는다.
- 한/영 형식을 질문 끝에 명시하고 정답에는 괄호·설명을 넣지 않는다. 출처 문항과 페이지, 선정 근거는 `note`에 기록한다.
- 단답 원본과 빌더가 현재 없으므로 등록 전에 문서에 지정된 경로를 복구하거나 최소 구현한다. 생성 JSON을 직접 편집하지 않는다.
- 변형 문제는 다른 방향으로 묻고 `variantOf`에 원문 key를 넣는다. 앱이 조회하는 원문 데이터에 해당 key가 있어야 한다. 교재 출처 표시는 `source`/`note`로 처리하며 출처 표기를 `variantOf`로 대신하지 않는다.
- 법규 숫자는 등록 시점의 공식 조문과 시행일을 확인한다. 확인되지 않은 숫자와 변동이 잦은 기관 목록은 보류한다.

## 5. 검증과 완료 조건

### 추출 완료

- 시작 시 확인한 전체 PDF 페이지에 저장 성공 또는 실패/텍스트 없음 사유가 있다. 빠진 페이지를 성공으로 간주하지 않는다.
- 추출된 모든 문항은 원본 파일과 PDF 위치로 역추적할 수 있다.
- 인접 페이지 중복, 문항 번호 재시작, 페이지 경계에서 이어지는 문제를 검수한다.
- 해설만 있는 문항·정답이 없는 문항·대응하지 않는 빈칸·문항 경계 불명확 항목이 보류 목록에 있다.
- ‘순회 완료’와 ‘내용 전부 복원 완료’를 구분한다. 표·그림·누락이 남으면 그 범위와 이유를 보고한다.

### 데이터 및 사이트 완료

- 각 등록 문항의 질문·정답 대응과 정답의 유일성을 확인한다. 서술형은 자동 문자열 채점 대신 자가 채점으로 처리한다.
- 기존 문항과 완전히 겹치는 학습 카드를 새 key로 중복 등록하지 않는다. 교재 원문 기록은 그대로 유지한다.
- 변환기를 만들면 페이지 경계 문항·중복·복수 소문항·누락 정답을 포함하는 작은 실행 가능한 검사 하나를 남긴다.
- `npm run check`를 통과한다. 현재 검사는 `questions/written`만 다루므로 별도 실기 JSON의 필수값·key·답안 대응·상태 검사를 같은 하네스에 추가한다.
- 현재 하네스는 길이가 100인 모든 파일에 과목당 20개를 강제한다. 새 교재 데이터에 수량을 맞추지 않고, 구현 때 해당 검사를 실제 기출 파일에만 적용하도록 범위를 고친다.
- 사이트 코드를 변경한 단계에서는 `npm run build`와 `npm run lint`를 실행하고, 용어 단답·복수 빈칸·서술형 각각의 문제 표시 → 답안 → 정답 공개 → 기록 → 복습 경로를 확인한다.
- 완료 보고에는 페이지 처리 범위, 검수 완료/보류 문항, 등록 문항, 남은 누락, 실행한 검사를 구분한다. 목표 수량 달성이 완료 기준은 아니다.

## 실행 순서

1. 한 페이지의 실제 파일 저장과 페이지 이동 검증.
2. 교재 앞부분에서 단답·서술·표 포함 사례를 확보하여 구조화 방식 검증.
3. 전체 페이지 원본 수집과 재시도 목록 정리.
4. 문항 구조화, 누락·교재 오류·정답 검수.
5. 검수한 실기 데이터를 내보내고 최소 자가 채점 모드 연결.
6. 필기 선정 기준에 걸리는 단답 후보만 기존 빌더를 통해 등록.
7. 하네스·빌드·린트·실제 풀이 흐름 검증 후 결과 보고.

우선 1~2단계에서 데이터 품질과 저장 경로를 확정한다. 이 문서는 구현 계획이며 현재는 사이트 배포나 원문 전체의 공개 게시를 수행하지 않는다.
